# System Administration {#module-system-admin}

The default installation will allow you to immediately begin using the system in a production capacity. There will be generic values set on the login page, the notification emails, and a few other places but you can quickly and easily change any of them via the System Administration. Therefore, it is suggested that you go into the System Administration immediately after install to customize it to your organization.

W> Regardless of any other customizations you do or do not make to your system, upon successful installation, you should immediately change the password of your admin user. If you fail to change your password, you are creating a significant to your Web2Project installation.

## The System Admin Page {#system-admin-page}

The System Admin page is split into these sections:

**System Status**

* System Configuration
* Reminders that need your attention: *Set the Admin Email Address* while it is still the default, *Apply System Updates* when database updates are waiting, *Select a Timezone* when the server time zone isn't set, and *Upgrade Available!* when a newer release is out

**Preferences**

* Default User Preferences
* System Lookup Keys
* System Lookup Values
* Custom Field Editor

**Modules**

* View Modules

**Language Support**

* Translation Management

**Administration**

* User Roles
* Users Permissions Information
* PHP Info

**Budgeting Setup** (only when *Display Budget Information* is on)

* Billing Code Table
* Setup Budgets

## Applying System Updates

After you upgrade, *Apply System Updates* runs the database migrations that haven't been applied yet. It lists any SQL errors it hits; a clean upgrade reports none. See the [Installation Guide](#upgrade-instructions).

## General Configuration

The first values that should be changed in your System Admin are the values listed here. This will ensure that your login page, emails, and page titles represent your organization. One of the most useful aspects is changing the “Email Prefix” to something meaningful and filter-able. The default is “[web2Project]”; something short and specific to your organization, such as “[acme-pm]”, lets people filter messages quickly with the rules common to most email clients.

The next aspect to change are the Calendar values. These values determine the display of every calendar throughout your system and even assist in the auto-calculation of task start and end dates in addition to durations. The Start and End Hour values are based on a 24-hour clock and the Working Days assume Monday = 1, Tuesday = 2, etc. The Calendar Minute Increment is not generally used in the Task scheduling and is more often used in the Events Management on the Calendar. Therefore, if your working schedule was 9am to 5pm Monday through Friday, your Start and End Hours would be 9 and 17 respectively while your Calendar Working Days would be 1,2,3,4,5.

The final configuration options commonly modified are the Default Module, Default Submodule and Default Tabbed Subview under *Start Up*. Together they determine the first page a user sees when they log in. By default it is the Calendar's day view.

While you're in System Configuration, also set the *Server Timezone* and the *System Administrator Email Address*. The System Admin page reminds you about both until they are set.

## System Configuration Reference {#system-configuration}

The settings are grouped by area. Hover over the (i) icon next to each setting for a short description.

### System

* **Company Name**: shown at the top of the sign-in box.
* **Debug Level** and **Show Debug Messages**: see [Turn on Debugging](https://docs.web2project.net/docs/turn-on-debugging.html). Leave them at 0 and off on a live system.
* **Enable Gantt Charts**: turns the Gantt charts on or off. They need PHP's `gd` extension.
* **Host Locale**: the default language for the site.
* **Log Changes**: records changes in the History module.
* **Page Size**: the number of records per page in long lists.
* **Page Title**: shown in the browser's title bar.
* **Memory Limit for Gantt**: raises PHP's memory limit while drawing Gantt charts, for example `64M` or `128M`.
* **Site Domain**: used to complete e-mail addresses entered without a domain.
* **Server Timezone**: the time zone of the server itself. Each user also sets their own time zone in *Preferences*.
* **System Administrator Email Address**: where system messages, such as new sign-up notices, are sent.
* **Check for Official Updates?**: checks for a newer release and shows *Upgrade Available!* on the System Admin page. **Last Check for System Updates** shows when it last checked.

### Users

* **Activate External User Creation**: shows a sign-up link on the sign-in page. It is on by default; see [Security Notes](#public-sign-up) before you leave it on.
* **Admin Username**: the login name of the administrative user.
* **Minimum Password Length** and **Minimum Username Length**.

### User Authentication Settings

* **User Authentication Method**: "Standard web2Project" (the web2project database), "LDAP" or "PostNuke".
* **Postnuke login also allows Standard Login**: with PostNuke authentication, also accept web2project logins.

### Budgeting

* **Currency Symbol**.
* **Display Budget Information**: shows budgets on projects, tasks and other modules, and adds the *Budgeting Setup* section to the System Admin page. See [Project Budgeting](https://docs.web2project.net/docs/project-budgeting.html).

### Calendar

* **Calendar Start Hour** and **Calendar End Hour**: the working day, from 0 to 23.
* **Calendar Minute Increment**: the steps in the calendar's time pickers.
* **Show MiniCals in Day View**.
* **Calendar Working Days**: a comma-separated list where 0 is Sunday. Monday to Friday is `1,2,3,4,5`.
* **Daily Working Hours**: the length of a working day, for example `8.0`.

### Files

* **Maximum File Size for Indexing**: files larger than this (in kilobytes) aren't indexed for searching. A negative value indexes every file.
* **Default File Indexing Parser**, **MS Word Indexing Parser**, **Html File Indexing Parser** and **PDF Indexing Parser**: the programs used to extract text from uploaded files for searching, for example `/usr/bin/strings` or `/usr/bin/pdftotext`.
* **Preserve File Settings on CI** and **Allow Editing of Previous Versions** belonged to file check-in and file versions, which v5.0 removed. They no longer do anything.

### LDAP Settings

* **LDAP Host** and **LDAP Port** (389 by default).
* **LDAP Version**: leave at 3 unless your server needs otherwise.
* **LDAP Base DN**: the base Distinguished Name for searches.
* **LDAP User Filter**: how to find a user, for example `(uid=%USERNAME%)`.
* **LDAP Search User** and **LDAP Search User Password**: the full DN and password of an account that can search the directory.
* **Full LDAP Connect String**: if set, overrides most of the settings above.
* **LDAP also allows standard login**: also accept users who exist only in the web2project database.

See [LDAP Authentication](#ldap) below for a worked Active Directory example.

### Locales

* **Translation Warning**: marks strings that have no translation.
* **Translation Alert String**: the marker added to them, `^` by default.

### Email Settings

* **Email Prefix**: added to the start of every e-mail subject.
* **Email Transport**: "PHP Default" (PHP's `mail()`) or "SMTP".
* **SMTP Host**, **SMTP Port** (25 by default) and **SMTP Secure** ("(None)", "TLS" or "SSL").
* **Host requires login**, **SMTP Username** and **SMTP Password**.
* **SMTP Server Timeout**: in seconds.
* **SMTP Debug**: shows the SMTP conversation on screen. Leave it off on a live system.
* **Queue Email for later sending**: puts e-mail in the event queue. It is sent when `queuescanner.php` runs from cron (see [Server and Database Configuration](#scheduled-tasks)) or, with *Scan Event Queue on Session Garbage Collection* on, when old sessions are cleaned up.

### Projects

* **Use ProjectDesigner to View Projects by Default.**: opens projects in ProjectDesigner instead of the project view.
* **Restrict Project Colour Selection**: limits project colours to the *ProjectColors* lookup values.
* **Template Projects Status Id**: the *ProjectStatus* value used for template projects (6, "Template", by default).

### Session Handling Settings

* **Session Handler**: "web2Project Extended Sessions" stores sessions in the database (the default); "PHP Default" uses PHP's own sessions.
* **Session Idle Time** (default `2d`) and **Session Maximum Lifetime** (default `1m`): in seconds unless followed by `h`, `d`, `m` or `y`. Only one letter is allowed, so `28h` is valid and `2d4h` is not.
* **Scan Event Queue on Session Garbage Collection**: processes the event queue when old sessions are cleaned up, as an alternative to cron.

### Start Up

* **Default Module**, **Default Submodule** and **Default Tabbed Subview**: the page users see after they sign in. The default is the Calendar's day view.

### Tasks

* **Overallocation Checking**: an unfinished feature. Leave it off.
* **Check Task Dates**: requires start and end dates on every task.
* **Default Company Filter** ("All Companies" or "Active User's Company") and **Default Task Filter**: the filters the Tasks list starts with.
* **Edit Multiple Task Assignments**: lets users change assignments for a block of tasks from the Tasks list.
* **Restrict Task Time Editing**: only the task owner, the project owner or an administrator can change task times.
* **Show All Task Assignees**: lists every assignee in task lists instead of the first one and a count.
* **Send Task Reminders**: e-mails the assignees when a task is due and every day it is overdue until it is complete. It needs the cron job.
* **Number of days warning for due tasks**: how many days before the due date the first reminder is sent.
* **Maximum number of reminders to send**: the total number of reminders for one task, including the early warnings.

## Roles & Permissions

The permissions system within Web2Project is based on phpgACL. While it provides a robust and powerful method of permissions handling, it can be complex and difficult to understand at times. The most important aspect to remember is that Roles apply to Modules and Permissions apply to individual items.

The four base roles at installation are Administrator, Project worker, Guest, and Anonymous and grant progressively more and more restrictive permissions.

Administrator – Administrators have complete access within the system and are able to do anything they choose. This includes creating, editing or deleting all information along with assigning Tasks, changing Users’ passwords, or even creating other Administrators.

Project worker – Project workers can create, edit, or delete any non-administrative information throughout the system. They can create Companies or Projects, assign Tasks, and log time against any task in the system. Most users will be a variation of this role.

Guest – Guests can view any non-administrative information. They cannot create, edit, or delete anything and therefore this works well as a basis for a Customer Role.

Anonymous – Anonymous can see the navigation and nothing else. While this role may seem useless at first glance, it can serve as a reasonable basis for highly limited Users who should only view specific Tasks such as third party organizations. By assigning this role as a start, no existing information in the system is made available although login is permitted.

The common aspect to all four of these Roles is that their privileges and limitations are associated to the Module level exclusively. They do not grant or deny privileges to specific companies, projects, or tasks. This is where permissions come into play.

Permissions are important to secure and protect information within Web2Project. Depending on an individual Users’ permissions, they may be able to manage anything within the system, anything within a specific company, or potentially only log time against their assigned tasks. Permissions allow very specific circumstances where the System Administrator can grant or deny individuals access to individual companies, projects, or even contacts and files.

Q> For performance, Web2Project works out each User’s effective permissions ahead of time instead of evaluating every rule on every request. It recalculates them when the User logs in and whenever a Role, a permission or a module changes, so changes normally show up on the User’s next page. If a User still sees old permissions, ask them to log out and back in.

## Session Management

One of the most common complaints with Web2Project 1.x involved the classic issue of “I was in the middle of doing X and my session timed out!”. In v2, this issue was resolved by the development of “web2Project Extended Sessions”, which is now the default. This allows the System Administrator to let Web2Project manage sessions and configure a custom “Session Idle Time” and a “Session Maximum Lifetime”.

Session Management for Web2Project can be handled in two different ways. The first is the standard PHP session model. When a system administrator is given the permissions to access and adjust the PHP configuration, this works well for most organizations. If Web2Project is being used in a shared hosting environment and the configuration cannot be changed, this often leads to session timeouts during periods of non-usage and can cause users to lose all information. Although this is not considered a bug in Web2Project, another option was created in response to concerns about this situation.

Within the Web2Project System Configuration, there are three values of interest titled “Session Handler”, “Session Idle Time”, and “Session Maximum Lifetime”. All of these values are tied specifically to the Users’ browser cookies and therefore do not transfer between computers or between different browsers such as Internet Explorer and Firefox.

To enable Web2Project’s management of sessions, set the “Session Handler” to “web2Project Extended Sessions”, the default for new installations. The other choice, “PHP Default”, uses PHP’s own session settings. Extended Sessions store sessions in the database and use the two values below; the defaults are 2d for the Idle Time and 1m for the Maximum Lifetime.

The Idle Time defines how frequently a user must be active in the system before they are automatically logged out. This is used to prevent Web2Project sessions from timing out at inappropriate times such as when a User begins to type data, then goes to lunch before returning to the session. Therefore, it is recommended to keep this set to a minimum of 1 – 2 hours. For organizations who allow a more relaxed security policy, this value can be set as high as the Maximum Lifetime.

The Maximum Lifetime defines the longest amount of time a user can go between logging in and subsequently being required to re-enter a password to access to the system. For many organizations, one to two weeks – represented as 7d or 14d respectively – is sufficient and will provide a reasonable amount of security. For organizations who need tighter security, this value can be reduced to hours using the suffix of “h”. 

For both the Session Idle Time and Session Maximum Lifetime, values are in seconds unless followed by one letter: h – hours, d – days, m – months, and y – years. Only one letter is allowed, so 28h is valid but 2d4h is not.

Each login is recorded in the access log, which feeds the Online/Offline status in the user list and the Active Sessions tab in User Admin. From that tab an administrator can end a single session or log a user out everywhere.

## LDAP Authentication {#ldap}

Part of the ongoing mission of the Web2Project Team is to provide seamless integration with existing infrastructures. Towards this goal, a System Administrator can choose to have users authenticate against and LDAP server such as Active Directory, a Lotus Notes Server, or OpenLDAP. Within the System Configuration, find the section labeled “LDAP Settings”. Set each of these values to point at your LDAP server, set “User Authentication Method” to LDAP, and save.

Using LDAP does not remove the requirements of configuring your Roles or Permissions but it does allow the User to avoid requiring yet another password. The first time someone logs in through LDAP, Web2Project creates their user account and a matching contact from the directory, with no Role. They appear under Inactive Users until an administrator assigns a Role.

LDAP logins need PHP's `ldap` extension.

### Example: Active Directory

First, create a service account in Active Directory. It only needs to be a member of the Domain Users group to search the directory.

Then go to System Admin → System Configuration and set:

* **User Authentication Settings**
  * User Authentication Method: LDAP
* **Users**
  * Activate External User Creation: off (optional, but recommended)
* **LDAP Settings**
  * LDAP also allows standard login: on, so the admin account keeps working
  * LDAP Host: the IP address or fully qualified name of a domain controller, for example `dc.peanutbutter.com`
  * LDAP Port: 389, the default port for Active Directory
  * LDAP Version: 3
  * LDAP Base DN: your domain, for example `DC=peanutbutter,DC=com` for peanutbutter.com
  * LDAP Search User: the full path to the service account, for example `CN=project,CN=Users,DC=peanutbutter,DC=com`. Use OU for an organizational unit and CN for a container; CN=Users is the default "Users" folder created when you install Active Directory.
  * LDAP Search User Password: the service account's password
  * LDAP User Filter: `sAMAccountName=%USERNAME%`

Now your users can log in with their Active Directory usernames and passwords. The first time someone logs in, Web2Project creates their user account and contact, with no role; give them a role in User Admin before they can do anything.

## Using SSL

Passwords and session cookies are sent with every login and request, so you should serve Web2Project over HTTPS. After you have the certificate installed, you can send all plain HTTP requests to HTTPS. On Apache with `mod_rewrite`, add the following to the .htaccess file in the root of your Web2Project installation:

{linenos=off}
    RewriteEngine on
    RewriteCond %{SERVER_PORT} !443$
    RewriteRule ^(.*) https://%{SERVER_NAME}/$1 [R,L]

Once this is in place, all requests to http://domainname.com/web2project/ become https://domainname.com/web2project/. On nginx, use a `return 301 https://$host$request_uri;` in the plain HTTP server block instead. See also [Security Notes](#security-notes).

## Email Notifications

Web2Project sends emails for a variety of reasons including task notifications, tasklog updates, event notifications, etc. Regardless of your host operating system, you have the options of sending via the default email transport defined in your php.ini – called “PHP Default” – or sending through a separate SMTP host. If the PHP default is available to you, it is unlikely that additional configuration will be necessary. If you use the SMTP host, you can specify additional login credentials for Web2Project to use and authenticate against, and choose TLS or SSL under *SMTP Secure*.

If you turn on *Queue Email for later sending*, messages wait in the event queue until `queuescanner.php` runs, so you need the cron job described in [Scheduled tasks](#scheduled-tasks). Task reminders always need it.

## Translation Management {#translation-management}

Web2Project ships with translations for Czech, Dutch, English, Farsi, French, German, Italian, Polish, Portuguese, Brazilian Portuguese, Russian, Spanish and Swedish in the `locales` folder. More are in the [locales repository](https://github.com/web2project/locales). To install one, copy its folder into `locales/`. The folder is named with the language's ISO code, such as `fr` for French or `pt_br` for Brazilian Portuguese.

Once a language is installed, each User can choose it under *Preferences* in the user menu. To make it the default, set *Host Locale* in System Configuration and the Locale in the Default User Preferences. If there is no translated term for the term requested, Web2Project simply shows the original English term. This is to ensure that every label is displayed regardless of the completeness of the translation.

Q> While the Translation Management does allow the System Administrator to change the language of the system, it can also allow much more. If you create a custom translation built on your organization’s terms and information, it can be treated as Jargon Management instead.

One of the options in the System Configuration is “Translation Warning”. This changes the default behavior of the Translation System slightly. When there is no translated term, instead of returning the original term, it appends the *Translation Alert String* (a caret by default). This is a simple way to test the completeness of a translation. Whenever you are working on a non-English Translation, it is encouraged to turn this on.

### Creating a translation

So you want to create your own Translation. The good news is that it's easy. Just follow these instructions to get started:

* Go to your web2project installation and locate the **locales** folder.
* Copy the **/path/to/web2project/locales/en** folder and its contents to, e.g. **/path/to/web2project/locales/sr**
  * In this example, we're translating from English - en, to Serbian - sr, so wherever you see **sr** you should change that to the short code of the language you're translating to.
  * Specific dialects of a language should be noted. For example, Portuguese is **pt** while Brazilian Portuguese is **pt_br**.
* Make the new folder writable by the user your web server runs as, so the translation editor can save to it. On Linux, for example:

{linenos=off}
    sudo chown -R www-data /path/to/web2project/locales/sr

* Use your web server's user in place of `www-data` (`apache` or `nginx` on some systems). Don't make the folder writable by everyone (`chmod 777`). Strings for Add On modules that keep their own translations are saved in the module's `locales/sr` folder instead, so make that writable too if you translate them.
  * If you're on a Windows system, make the folder writable by the web server's user.
* Open up in your favourite editor the **/path/to/web2project/locales/sr/lang.php** file and edit it according to the instructions in that file. When you're done, save and close.
* Log in to your web2project installation, go to *System Admin* and then to *Translation Management*.
* At the top you will see two select boxes: the first for the part of the system you're translating (**Module**), the second for the **Language**.
* Choose the part of the system you want to translate and the new language you are translating to.
* Translate, hit submit. That's about it.
* When you're done, make the folder read-only for the web server again.
* We'd appreciate if you'd contribute [your translation to web2project](https://github.com/web2project/locales). Simply follow [the directions in our README](https://github.com/web2project/locales#contributing) and your contribution will be shared with thousands. Thank you! :)

The editor only saves to languages that already have a folder in `locales/` and to installed modules.

### Translation file format

Since v5.0, translation (`.inc`) files are read as data, not run as PHP. Each line is a quoted English string, `=>`, and the quoted translation, followed by a comma:

{linenos=off}
    'Add a Todo'=>'Ajouter une tâche',
    "Task Name"=>"Nom de la tâche",

Single or double quotes both work, and comments are allowed. An entry that contains anything else, such as a variable, a function call or text joined with `.`, is skipped, and that string shows in English. Translation files written for older versions usually work unchanged; check any that built strings with PHP code.

`lang.php` in each language folder is still PHP; it describes the language and isn't affected.

If you have questions or comments, ask in the [community discussions](https://github.com/orgs/web2project/discussions).

## Default User Preferences

This screen is identical to the individual Users’ preference screens. As you create new Users in Web2Project, you can use this screen to ensure their defaults are set correctly. This only applies to Users created after the changes are made to the Default Preferences. Each User can change their own under *Preferences* in the user menu, and an administrator can change them from the User's page in User Admin. The preferences are:

## Custom Field Editor

Quite often a User will want to attach additional information which does not already fit within Web2Project such as “Year Established” for a Company or “Codename” for a Project. The Custom Field Editor is a quick and simple way of adding new fields to Companies, Projects, Tasks, Calendar (events), Contacts and Users without having to change the database, create custom code, or change any templates. To add these fields, simply follow this process:

1. Select “Custom Field Editor” within the System Administration.
1. Select the add icon next to the relevant module.
1. Input a “Field Name/Identifier”. This is the name of the html form element and should consist exclusively of alphanumeric characters. For example, year_established would be a valid value while “year established” is not.
1. Input a “Field Description”. This is the label used next to this field whenever it is displayed.
1. Select a “Field Display Type” to determine the type of input field. “Text input” or “textarea” are sufficient for many uses. For a list, enter the “List of Options”.
1. Choose whether the field is published (“Field Published”) and set its “Field Display Order”.
1. Add “HTML Tag Options” if you need them.

All fields added through the Custom Field Editor are global across the entire system regardless of the overall organization of the system. Therefore, in our above example, every Company would have this field available. The fields appear on the module's add/edit form and view in their Field Display Order.

Add On modules can't add their own custom fields through the editor yet.

## Billing Codes and Budgets {#billing-codes}

For organizations who perform contracting for other organizations often have reporting requirements involving multiple billing codes, numerous billing rates, and a variety of invoicing systems which may vary from customer to customer. The *Billing Code Table* gives the administrator the option to set billing codes with distinct billing rates. Each code has a code, a value (the cost per hour), a description, a billing category from the *BudgetCategory* lookup values and, optionally, a company. These codes immediately become available in the task log's cost code drop-down and in the Reports Module.

*Setup Budgets* sets budget amounts per company, period and billing category. Both pages are listed under *Budgeting Setup* on the System Admin page, which only appears when *Display Budget Information* is on in System Configuration. See [Project Budgeting](https://docs.web2project.net/docs/project-budgeting.html) on the docs site for how the budgets and costs fit together.

## System Lookup Values

System Lookup Values hold the choices themselves. This includes standard drop-down lists and tabs such as those on the Projects list.

For example the Projects list tabs come from the "ProjectStatus" values:

{linenos=off}
    0|Not Defined 1|Proposed 2|In Planning 3|In Progress 4|On Hold 5|Complete 6|Template

Changing these values changes the tabs, but you can't change the "All Projects", "All Active" or "Archived" tabs, which are built in.

Other commonly edited lists are *FileType* (the Files categories), *BudgetCategory* (billing and budget categories) and *ResourceTypes* (the Resources types).

It is strongly recommended you do not modify these settings unless you are comfortable with what you're doing. Modifying the wrong system values could have undesired results.

## View Modules {#view-modules}

View Modules lists the installed and available modules. From here you can install, activate or disable, upgrade, configure and remove modules, change their order, and choose whether each appears in the navigation.

* The arrows move a module up or down, which also changes its position in the navigation.
* Select "visible" or "hidden" to show or hide it in the navigation.
* Some core modules, such as Reports and Resources, are installed but hidden or disabled by default.
* Add On modules are uploaded with *Select a module to upload*, if the `modules` folder is writable, or copied into `modules/` by hand. Check them against [Updating Add On Modules for v5.0](#upgrading-modules) first.
